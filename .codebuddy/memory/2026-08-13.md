# 2026-08-13

## osbuilder CLI 分析任务

分析了 `cmd/osbuilder` 的命令层级与配置管理，并落地了严格简化版示例。

### 命令层级
- 入口 `cmd/osbuilder/osbuilder.go` 极薄，仅构造+运行根命令。
- 根命令在 `internal/osbuilder/cmd/cmd.go: NewOSCtlCommand`：用 `templates.CommandGroups` 分组展示 + `AddCommand` 建 Cobra 树（支持多级如 `create project`）。
- 统一签名 `NewXxxCmd(f cmdutil.Factory, ioStreams)`，叶子用 Options 模式（Complete/Validate/Run），中间节点只路由。

### 配置管理
- 配置逻辑不在入口，集中在 `cmd.go`：Options 结构体(`util/options/options.go`) + `AddFlags` + `viper.BindPFlags` + `cobra.OnInitialize(core.OnInitialize(...))`。
- `core.OnInitialize` 在 `onexstack/pkg/core/config.go`：读 `osbuilder.yaml`（搜索 `~/.onexstack` 和 `.`）+ `OSCTL_*` 环境变量。
- 优先级：默认值 < 文件 < 环境变量 < --config 指定 < 命令行 flag。
- 通过 `cmdutil.NewFactory(opts)` 把配置注入子命令。

### 交付物
1. `docs/cli-config-management.md` — CLI 配置管理文档。
2. `examples/osbuilder-simplified/` — 独立 module 简化版（含 viper 配置机制），已 `go mod tidy` + 编译运行验证通过。
   - 注意：viper v1.19 已移除 `viper.OnInitialize`，简化版用 `cobra.OnInitialize` 包裹（与真实代码一致）。
   - PowerShell 不支持 `KEY=val cmd` 语法，验证环境变量需用 `$env:KEY='val'`。
   - **目录对齐**：原简化版把 options 放在 `internal/cmd/options/`，后为与真实仓库 `internal/osbuilder/{cmd, util/options}` 严格对齐，已移到 `internal/util/options/`（options 与 cmd 同级，因为是共享基础设施）。同步更新了 README 目录结构与对应表。
   - **两个 options 包**：真实仓库有 `cmd/options`（= `osbuilder options` 帮助子命令，打印继承 flag，与配置无关）和 `util/options`（= 全局配置结构体，绑定 viper）。两者同名但职责不同。简化版均已复刻：`internal/cmd/options/options.go` 和 `internal/util/options/options.go`。cmd.go 中给配置包起别名 `clioptions`（与真实 cmd.go 一致）避免 import 同名冲突。文档与 README 均补充了「两个 options 包区别」说明。

### es 命令：领域配置（子命令级）范例
- 新增 `internal/cmd/es/`（`es.go` 中间节点 + `get/get.go` 叶子 + `options/options.go` 领域配置 `ESOptions`：addr/index/username/password）。
- 设计要点：连接 ES 这类只服务于单一子命令的配置属于**领域配置**，不应进全局 `Options`（`util/options`）。flag 挂在子命令自身（`--es.addr` 等），前缀 `es.` 隔离，不污染 `osbuilder options` 显示的全局 flag 表。
- 优先级合并：flag 默认值(NewESOptions) < 文件 es.* < 环境变量 OSCTL_ES_* < flag 显式值。
- **关键坑**：viper v1.19 的 `UnmarshalKey` 不会读取 `BindPFlags` 注册的 flag 默认值。故 `ESOptions.Complete(cmd)` 改为「`cmd.Flags().Lookup(...).Value.String()` 兜底 + `viper.IsSet("es.xxx")` 覆盖」手动合并。BindPFlags 放在 NewCmdGet 构造期（与全局 PersistentFlags 时机一致）。已验证 5 种场景全部正确。
- 文档 `docs/cli-config-management.md` 新增第 10 节「领域配置 vs 全局配置」+ es 示例；README 新增 es 命令说明与目录结构。均已编译 `go build ./...` + `go vet ./...` 通过。

### 原版 `--config` 失效 bug（待用户后续修复，本次未改）
- **位置**：`internal/osbuilder/cmd/cmd.go:201`
  ```go
  cobra.OnInitialize(core.OnInitialize(ptr.To(viper.GetString(clioptions.FlagConfig)), "OSCTL", searchDirs(), defaultConfigName))
  ```
- **根因**：`viper.GetString(clioptions.FlagConfig)` 在**构造根命令期**执行，flag 未解析返回 ""；`ptr.To("")` 得非 nil 指针指向 ""，闭包 `if configFile != nil` 为真 → `viper.SetConfigFile("")`，`ReadInConfig` 找不到空路径文件，错误被 `_` 忽略 → `--config` 指定的文件被完全丢弃，静默回退搜索目录/默认。
- **与简化版关系**：与简化版修复前完全一致；简化版已改为延迟求值 `func() *string`（config.go 的 OnInitialize 签名 + cmd.go 传 `func() *string { return getConfigPtr(viper.GetString(...)) }`）修复，已验证生效。
- **为何运行时看不出**：(1) `ReadInConfig` 错误被 `_` 静默；(2) 原版子命令几乎不调 `GetOptions()`，无命令打印 user.* 配置值，无法正面观测。已实测 `--config /不存在文件 version` 静默 EXIT=0。
- **外部依赖**：`core.OnInitialize` 来自 `github.com/onexstack/onexstack/pkg/core`（go.mod 锁 v0.3.21，路径 `D:/gopath/pkg/mod/github.com/onexstack/onexstack@v0.3.21/pkg/core/config.go`）。它的签名是 `OnInitialize(configFile *string, envPrefix string, loadDirs []string, defaultConfigName string)`，与构造期求值陷阱同源。
- **修复方案（待定）**：方案 A 改 `core.OnInitialize` 签名（跨仓库，影响面大）；方案 B 根命令 `PersistentPreRunE` 里动态 `viper.SetConfigFile(viper.GetString("config"))` + `ReadInConfig()`，绕开构造期陷阱（不改 core 签名，推荐）。用户决定先记录、后修。
- **构建注意**：原版 `go build ./...` 会因 `internal/osbuilder/tpl` 和 `examples/template` 两个**脚手架模板目录**（含 `{{.Placeholder}}`）报语法错，与逻辑无关；应改用 `go build ./cmd/osbuilder` 或 `./internal/osbuilder/...`（但后者仍递归进 tpl，直接 `./cmd/osbuilder` 可成功）。
